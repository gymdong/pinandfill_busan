# FR-004: API-011 Fake 추천

## 계약과 조립

PR #1 최신 head `fa293de256444c355928eb35e9ac65f24f259d78`의 타입과 엔드포인트를
읽기 전용으로 재확인했다. `POST /api/trips/{tripId}/waypoints/suggest`는
`fromBlockId`, `toBlockId`, `thresholdMin: 10|15|30`, 선택적 `sessionCoords`를 받는다.
응답은 `{candidates:[{place,detourMin,stayMin,crowd,reason}]}`이며 최대 3개다.
확인 가능한 후보가 없으면 HTTP 200과 `{candidates:[]}`를 반환한다.

`TripService(..., recommender=WaypointRecommender(candidates, places, routes, weights))`로
명시적으로 조립한다. 기존 API-006·009 조립 인자는 그대로이며 recommender는 선택적이다.
미설정 상태의 추천 요청은 기존 오류 처리 경계를 통해 503으로 반환한다. 실제 DB나
외부 클라이언트는 추가하지 않았다. HTTP Fake 조립 예는 `tests/integration/test_waypoint_api.py`에 있다.

## 후보 평가

1. 여행 저장 상태 안에서 같은 날짜의 순방향 인접 블록인지 확인한다. 잘못된 ID·역순·
   비인접·날짜 간 슬롯은 400/ERR-001이며 일정을 저장하지 않는다.
2. 출발 시각과 양쪽 좌표가 필요하다. 기준 이동시간은 현재 이동수단으로 공급자에서
   조회한다. 오래된 저장 구간의 이동수단·시각을 무조건 재사용하지 않는다.
3. `CandidateProvider`는 방문 날짜별 PUBLIC 참조, 제공된 체류시간, 취향·대표성 신호와
   선택적 혼잡 정보를 제공한다. 카카오 후보는 모델에서 허용하지 않는다.
4. 같은 날짜에 후보를 임시 삽입하고 기존 엔진의 영업시간·휴무·브레이크타임·체류시간·
   하루 시간창·후속 고정시간 검증을 재사용한다. 변경된 후속 블록까지 검증한다.
5. SRS FR-004의 공식 `detour=t(A→X)+t(X→B)−t(A→B)`로 계산하고 임계값 이하만 남긴다.
   **체류시간은 우회시간에 더하지 않지만 실제 시간 제약에는 반영한다.**
6. 설정된 점수 내림차순, 같은 점수는 PUBLIC ID 사전순으로 정렬해 최대 3개를 반환한다.
   이유에는 우회·체류시간과 검증한 제약을 표시한다. 혼잡이 없으면 `crowd:null`이다.

추천은 조회다. 원래 state의 seq·시간·블록·구간을 변경하거나 저장소 `save`를 호출하지
않는다. 실제 수락·저장은 기존 API-006을 호출한다. 후보 삽입 시뮬레이션의 ID와 경로 시각은
API-011 결과에 노출하지 않으므로 동일 공급자 데이터와 설정에서 결과가 재현된다.

## 미확정 값과 보수적 처리

SRS의 점수식은 `취향 일치 + 평점·대표성 − 우회 비용 − 예상 혼잡 패널티`다.
`ScoreWeights`는 각 항의 가중치와 `missing_crowd_penalty`를 **필수 주입**받으며 운영
기본값을 정의하지 않는다. 후보 취향·대표성 신호도 공급자가 명시해야 한다. 테스트의
수치들은 합성 데이터일 뿐 운영 정책이 아니다. 신호의 정규화·평점 누락 처리·가중치와
혼잡 누락 패널티는 데이터 담당자와 합의해야 한다.

아래는 검증 가능한 후보만 반환하기 위한 현재의 처리이며 문서에 확정된 제품 정책으로
간주하지 않는다.

- 후보 체류시간·좌표·필수 표시 메타데이터·영업시간·경로 시간이 없으면 후보 제외.
  시작 시각·기준 경로·양쪽 앵커 좌표가 없으면 빈 목록. 임의 기본값·직선거리 시간 없음.
- 출발 앵커의 체류·시간창·고정 시각 불일치가 있으면 오래된 계산 시각을 근거로 추천하지
  않고 빈 목록을 반환한다. API-009에서 먼저 일정을 정합하게 계산해야 한다.
- 기존 후속 장소의 시간·좌표·이동시간은 검증 가능해야 한다. 기존 장소 영업시간만
  미상인 경우에는 추천 이유에 별도 확인 필요를 명시한다. 후보 자신의 영업시간 미상은 제외한다.
- 중복 PUBLIC ID를 가진 모호한 후보 레코드는 모두 제외한다. 양쪽 앵커와 같은 장소도 제외한다.
- 동점의 ID 정렬은 재현성용 구현 규칙이다. 다양성·인기도 등 추가 제품 순위를 만들지 않는다.
- 음수 우회시간은 공식 결과를 그대로 보존한다. 0으로 자르기·추정값 불일치 보정은 미정이다.
- 후보가 검증 불가해서 비어 있는 경우와 실제 후보가 없는 경우를 현재 계약은 구분하지 않는다.
  이유 코드 추가는 별도 API 합의가 필요하다.

## 카카오 데이터 경계

카카오 앵커는 ID·URL만 저장된 기존 상태를 사용한다. 좌표는 이번 요청 컨텍스트로만
해석하며 공공 장소 공급자에서 조회하지 않는다. 컨텍스트를 추천기나 저장소에 보관하지
않는다. 좌표가 없는 다음 요청에서 이전 요청 좌표를 재사용하지 않는다.
후보 결과는 PUBLIC만 포함한다. 오류는 기존 정적 메시지로 변환하며 원문 예외·입력값을
응답이나 로그에 쓰지 않는다. 요청·응답 캐시를 추가하지 않았고 HTTP는 `no-store`다.

## 실제 TMAP·ODsay 연결 전

- 현재 RouteProvider는 출발 시각 인자가 없다. 실제 시간대별 대중교통 조회를 위해 날짜·
  출발시각·시간대와 결과 신선도 계약을 확정해야 한다.
- SRS의 추정 사전 필터 → 점수 상위 후보만 실제 경로 확인 단계를 분리하고 검색 반경,
  후보 수 제한, API 호출 예산·RouteQuotaGuard·타임아웃·폴백을 구현해야 한다.
- PUBLIC 장소별 날짜 정규화 영업시간·체류시간·취향·대표성·혼잡 신호 공급자를 연결해야 한다.
- 카카오 좌표가 공급자 내부 캐시·HTTP 디버그 로그·APM·예외 locals에 남지 않는지 검증해야 한다.
- 실제 DB의 여행 소유권·읽기 스냅샷 일관성·삽입 트랜잭션은 기존 단계와 마찬가지로 미구현이다.

이번 구현은 모든 경로를 Fake 공급자로 계산한다. 실제 키·TMAP·ODsay·DB·팀원 화면은 건드리지 않는다.

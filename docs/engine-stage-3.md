# API-006·009 Fake 통합

## 이번 단계의 계약

- `POST /api/trips/{tripId}/blocks`: 기존 인접 블록 사이에 삽입하고
  `{schedule, violations}`를 반환한다. `violations`는 schedule의 목록과 같다.
- `POST /api/trips/{tripId}/schedule`: 명시된 방문 순서와 날짜별 시작 시각을 기준으로
  계산·검증하고 `{days, violations, conflicts}`를 반환한다.
- 순서값 간격이 있으면 기존 seq를 그대로 사용한다. 간격이 없으면 **삽입한 날짜만**
  방문 순서대로 10, 20, 30…으로 재번호화한다. seq는 식별자가 아니며 기존 블록 ID,
  방문 순서와 고정 시작·종료 시각은 보존한다. 이후 삽입에도 같은 규칙을 적용한다.
- 두 삽입 앵커는 존재하는 같은 날짜의 인접 블록이어야 한다. 위치 미지정, 시작·끝 단독
  삽입, 최초 자동 배치는 아직 지원하지 않는다. 사용자의 이번 재번호화 허용 외 정책을
  새로 정하지 않는다.
- API-009의 날짜별 첫 블록은 이미 계산된 시작·종료 시각 또는 명시된 고정 시간창이
  필요하다. 빈 일정, 시작 시각 없는 일정, 비어 있지 않은 미정의 `options`는 거절한다.
- 이동시간 불명은 null과 확인 필요 경고로 반환한다. 영업시간·휴무·미고정 블록의
  시간 위반은 200 응답에 표시한다. 자정 초과 경고는 여러 날짜의 재계산에서도 유지한다.

## 구성과 저장 경계

`create_app(trip_service=TripService(repository, engine, stay_duration))`으로 의존성을
명시적으로 주입한다. `engine`은 기존 `BasicItineraryEngine`, 저장 경계는 `TripRepository`,
테스트 구현은 `FakeTripRepository`다. 체류시간 공급자는 PUBLIC ID 또는 카카오 ID·URL만
받고, 값을 모르면 None을 반환한다. 테스트의 30분은 테스트 데이터이며 운영 기본값이 아니다.

`tests/integration/test_trip_api.py`의 `setup_api`가 실행 가능한 전체 Fake 조립 예다.
기본 `app.main:app`에는 운영 저장소·공급자를 연결하지 않았으므로 health는 동작하고
두 일정 API는 구성 전 503을 반환한다. 실제 키·DB·외부 경로 API는 사용하지 않는다.

서비스는 조회→계산→최종검증→저장을 단일 로컬 잠금 안에서 처리한다. 모든 날짜의
계산이 성공하고 고정 시각 충돌이 없을 때만 저장한다. 이 잠금은 한 프로세스의 Fake
검증용이며 운영 DB의 트랜잭션·버전 충돌 제어를 대체하지 않는다. 인증·여행 소유권
검사, 저장 스냅샷·되돌리기는 이번 단계에 포함하지 않는다.

카카오 이름은 입력 모델에서 거절한다. 좌표는 요청별 `CalculationContext`에만 들어가며
저장소에는 `TripWindow`와 ID·URL 기반 `ScheduleState`만 전달한다. 응답·예외 메시지에
입력값이나 원래 공급자 예외를 삽입하지 않으며 요청·응답·예외 로깅을 추가하지 않는다.
HTTP 응답에 `Cache-Control: no-store`를 설정한다. 후속 미들웨어·DB·APM이 원문 body,
예외 locals 또는 `ValidationError.errors()`를 수집하지 않도록 별도 통합 검증이 필요하다.

## 오류 계약과 남은 합의

현재 프런트가 제안한 최소 `{error: {id, message}}`를 재사용한다. 필드별 오류·충돌
상세 JSON은 정의하지 않았다. 요청 원문, 동적 필드명, 좌표를 오류로 되돌려주지 않는다.

| 상황 | HTTP / 코드 | 경계 |
|---|---|---|
| 요청 형식, 식별자, 인접성 오류 | 400 / ERR-001 | 정적 안내 |
| 미합의 자동 배치·체류시간 공급원 | 400 / ERR-001 | 현재 미지원 요청 처리; 제품 UX 합의 필요 |
| 고정 블록 지정 시간의 이동·체류·하루 시간창 충돌 | 409 / ERR-009 | 날짜 분리 안내, 저장하지 않음 |
| 영업시간·휴무 등 일반 위반 | 200, violations | 저장하고 경고 표시 |
| 없는 여행 | 404 / ERR-016 | 기존 프런트 코드 재사용 제안 |
| 미설정 서비스, 필수 표시정보 누락, 공급자 실패 | 503 / ERR-017 | 기존 프런트 코드 재사용 제안 |

SDD ERR-016은 본래 권한·공유 링크, ERR-017은 DB 장애를 설명한다. 일반 여행 조회와
공급자 실패에 대한 확장 매핑은 팀 확인 대상이다. ERR-009의 충돌 블록 목록·날짜 분리
제안의 구조와 409 발생 시 UI가 기존 일정을 유지하는 방식도 합의해야 한다. 현재는
상세 필드를 발명하지 않고 정적 메시지로 원인과 날짜 분리 제안을 전달한다.

## 검증

`backend`에서 다음을 실행한다. PR #4 설정 파일은 변경하지 않고 CLI 옵션만 적용한다.

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/ruff.exe check --select E,F,I,B,UP --line-length 120 --target-version py312 app tests
.venv/Scripts/ruff.exe format --check --line-length 120 --target-version py312 app tests
.venv/Scripts/mypy.exe app
```

기존 55개 중 바뀐 동작을 기대하던 2개(간격 없는 삽입 거절, HTTP 라우트 부재)는
새 동작으로 갱신했다. 나머지 기존 검증을 보존하고 재삽입·여러 날짜·HTTP 오류·비저장
통합 검증을 추가했다. 기존 Python 3.14 환경에서 검증하며 Python 3.12 및 uv는 설치되어
있지 않아 PR #4 uv.lock 환경 검증은 미수행이다. 설정·잠금파일·기존 가상환경을 대체하지 않았다.
